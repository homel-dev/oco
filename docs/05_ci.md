# OCO Continuous Integration

## Scope

OCO CI has two layers.

The organization layer is provided by
`homel-dev/.github/.github/workflows/repository-ci.yml` and enforces shared
repository hygiene.

The OCO layer renders and validates the Kubernetes topology owned by this
repository.

## Triggers

CI runs on:

- pushes to `main`;
- pull requests;
- manual `workflow_dispatch`.

The workflow declares read-only repository permissions and does not use
deployment credentials.

## Organization checks

The shared workflow validates:

- text and Markdown hygiene;
- local Markdown links;
- numbered canonical documents;
- YAML style and syntax;
- Bash syntax;
- ShellCheck errors;
- obvious committed credential material;
- GitHub Actions pinning policy.

The organization workflow is currently referenced by `@main` for bootstrap.
After the organization `.github` change is committed, this reference SHOULD be
replaced with that reviewed commit SHA.

## OCO-specific checks

OCO renders:

```text
k8s
k8s/backend
k8s/backend/overlays/tempo-minio
```

The rendered manifests are validated with Kubeconform against Kubernetes 1.37.

`scripts/ci/validate_oco.py` additionally enforces contracts that Kubernetes
schema validation cannot express:

- the backend contains exactly one Alloy, VictoriaMetrics, VictoriaLogs, and
  Tempo Deployment;
- the backend contains no DaemonSet;
- OCO does not introduce Prometheus or Loki backend Deployments;
- backend containers use explicit image tags;
- backend containers declare requests and limits;
- VictoriaMetrics, VictoriaLogs, and Tempo persistent volumes are present;
- backend NetworkPolicy objects are rendered;
- VictoriaMetrics retention and free-space floor use supported flags;
- VictoriaLogs retention, disk cap, and free-space floor use supported flags;
- Alloy node log mounts remain read-only;
- Grafana provisions exactly the three standard shared datasource UIDs;
- the Tempo MinIO overlay uses the dedicated `observability-tempo` bucket and
  `tempo-minio` Secret contract;
- backend/platform Task commands remain inside the Task v3 `tasks` mapping.

## Local validation

Requires Python, `kubectl`, Docker, and network access for the pinned
Kubeconform image:

```bash
task ci:validate
```

Runtime smoke and persistence validation remain separate operational gates.
Static CI does not claim that an unavailable cluster is healthy.
